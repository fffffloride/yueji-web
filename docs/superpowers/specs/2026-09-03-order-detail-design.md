# 订单详情页设计

日期：2026-09-03  
状态：已确认

## 1. 目标与范围

以现有确认订单页为视觉基准，实现小程序订单详情页，接通现有订单详情、取消、支付、好友代付、赠礼和预约能力。页面使用真实接口数据，不改后端，不增加依赖。

本轮不增加物流、退款申请、售后进度、客服会话或新的订单时间线；当前服务订单没有这些能力。

## 2. 页面结构

采用已确认的 A「状态主视觉」方案：

1. 顶部状态区使用墨绿主视觉，展示 `statusLabel` 和当前状态的简短引导。
2. 项目清单沿用确认订单页的图片、名称、规格、单价与数量布局；赠礼受赠人不展示金额。
3. 到店服务区按真实数据显示：待核销且有 `verifyCode` 时展示核销码；可预约时提示并由底部按钮打开现有预约抽屉；已有预约时只展示现有预约状态，不虚构日期与门店。
4. 联系信息展示联系人、手机号和备注；受赠人视图因接口不返回购买人隐私而隐藏整块。
5. 金额明细复用确认订单页的商品金额、会员优惠、优惠券、积分抵扣与实付层级；受赠人视图隐藏整块。
6. 订单信息展示订单编号、下单时间，以及服务端已有的取消原因、核销时间等状态字段。
7. 有可用操作时显示固定底部栏；没有操作时页面自然结束，不保留空白按钮栏。

## 3. 状态与操作

- 待付款：取消订单、好友代付（`canProxyPay`）、继续支付。
- 待核销：赠送好友或查看赠礼记录、预约到店（`canBookAppointment`）。
- 已核销、已完成、已取消、已退款：只展示结果信息，不制造无接口支持的操作。
- 受赠人：展示好友赠礼语义、项目、核销码和预约能力；隐藏购买金额及购买人联系信息。

所有按钮继续以服务端状态和能力字段为准，页面不自行推导权限。

## 4. 数据与交互

- 路由继续使用 `pages-sub/order/detail/index`，从查询参数读取 `id`。
- 首次进入和下拉刷新调用现有 `OrderAPI.getDetail(id)`。
- 支付复用 `PayAPI.create`、`invokeWechatPayment` 和支付结果页跳转。
- 取消复用 `OrderAPI.cancel`，确认后重新拉取详情。
- 预约复用 `YjAppointmentDrawer`；成功后重新拉取订单，可选择进入“我的预约”。
- 赠礼和好友代付复用现有订单列表页的目标路由和参数。
- 图片失败时显示固定尺寸的“悦己”占位，不改变布局。

## 5. 异常与边界

- 缺少订单 ID 时直接显示“订单参数不完整”。
- 首次加载显示统一加载态；失败或订单不存在时显示统一网络空态和重试。
- 提交操作期间禁用重复点击；失败消息继续由现有请求层统一提示。
- 长商品名两行截断，长订单号和备注允许换行，底部安全区由 `YjPage` 处理。
- 联系信息、金额、核销码等字段缺失时隐藏对应行或区块，不显示伪造占位值。

## 6. 验收

- 至少覆盖待付款、待核销、已取消和受赠人四种展示状态。
- 375×812 与 430×932 下无横向溢出、底部按钮遮挡或内容断层。
- 待付款的取消、支付与代付，以及待核销的预约、赠礼入口均走现有真实链路。
- 运行订单详情最小状态自检、类型检查、H5 构建和微信小程序构建；H5 浏览器交互按项目 UI 流程验收。
